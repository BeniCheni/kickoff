## Human review (Beni, 1 Sep 2026) — two items, act on both

Beni reviewed the PR in the GitHub UI and routed his feedback through this prompt rather than
PR comments — the AI-driven review is the workflow now. Resolve both items and record the
resolutions in the PR conversation, the same way you record precedence resolutions.

**1. Cadence: twice a day, at noon and midnight Brooklyn time — not every four hours.**
GitHub cron is UTC and does not follow DST. Use `0 4,16 * * *` — exactly midnight and noon
EDT; an hour early (23:00 and 11:00 ET) once EST starts on 1 Nov 2026 — and say so in the
workflow's header comment; don't get clever with two crons. Midnight ET catches every
European result of the day; noon ET catches the early weekend kickoffs and the weekday
announcements. Update every place the cadence is stated: `sync.yml` (the `cron:` line and
the header comment), `README.md` (twice — "What it does" and the Data source paragraph),
`CLAUDE.md` ("Scheduled sync"), `CHANGELOG.md`, `docs/v0.2.0-proposal.md` ("Shape of the
build" and its prose), and the row-13 text in `docs/v0.2.0-ideas.md`. Grep for "four hours"
and "every few hours" before you call it done.

**2. Gate the run on "are there any Big-5 fixtures today?" — Beni's ask, and the honest answer.**
Beni's idea: have the job check first whether any Big-5 match is on today and, if not, skip
the rest to save the runner's time; only sync when there are matches, new results, or fixture
updates. He asked to be corrected if the premise is wrong. Two facts change the design:

- `npm run sync` *is* the check. Nothing can know whether anything moved without fetching the
  window and diffing it — ESPN offers no "did anything change?" endpoint, and the diff engine
  is what turns the scoreboard into knowledge. The fetch is ~63 small requests and the whole
  job runs in about a minute on a GitHub-hosted runner; Actions minutes are free on a public
  repo. There is nothing to save in front of the fetch.
- The days with no matches are exactly the days fixture *updates* land. The committed snapshot
  has zero Big-5 fixtures on 1, 2, 8, 9 and 10 September — and the eight Ligue 1 kickoffs that
  went from placeholder to a real TV slot in PR #5 were fetched on Tuesday 1 September, a
  zero-fixture day. A "no match today, skip" gate would have missed them; likewise midweek
  postponements and the Premier League's monthly TV picks.

So: **do not add a match-day gate in front of the fetch.** Where Beni is right is the waste on
the *other* side of the fetch: today every run opens or updates a PR even when the diff engine
reports "no changes", because the `changed` gate keys on `git diff --cached --quiet` and every
run rewrites 959 `fetchedAt` stamps — the "Nothing changed" step is unreachable (also in the
appendix). Fix that instead:

- Make `changed` mean "the diff engine reported at least one change, or a standings rank
  moved". The cleanest seam: have `sync.ts` emit a stable machine-readable line (for example
  `report: changes=N standings-moves=N`) or write the report to a file, and let the workflow
  read that rather than parse prose. Keep the exit-code contract (0 / 1 / 2) intact.
- When nothing moved: no commit, no push, no PR — the step summary says so. If a
  `sync/scheduled` PR is already open from an earlier change-bearing run, leave it alone.
- Record the consequence honestly in the proposal and `CLAUDE.md`: the app's `synced` stamp
  and staleness banner then measure time since the last *change-bearing* sync a human merged,
  so through a quiet stretch (an international break) the banner goes amber and then red even
  though the bot verified nothing moved. That is the price of "no auto-merge"; the seam the
  proposal names — auto-merging an *empty* report once the diff engine also reports result
  and team-name changes — is the fix, and it stays out of this release.
- Put whatever pure function decides "changed" under a unit test; verify the workflow's branch
  of it with a dispatch run (a dry run, then a real run on a quiet day that ends at "Nothing
  changed" with no PR).

Reply to Beni's "correct me if I'm incorrect" in the PR comment in one line: he is right that
`npm run sync` is what fetches and diffs; the pre-check he imagined is that same fetch.

## Review method — verify, don't vibe

**Static pass.** Read every new/changed file completely. Hunt these classes specifically:

- **Data honesty** — the house religion. Can the sync now write anything it doesn't
  understand? Trace `normalizeEvent` → `fetchWindow` → `sync.ts` for every exit path: is
  there any route to a write after an `UnmappedStatusError`, a cap hit, or a shrink trip?
  Does `--check` share every guard? Can the shrink guard misfire on a legitimate shrink (a
  cup rolling out of the window, a winter break, the rolling window's edge)?
- **Time** — `src/lib/clock.ts` and every `useNow()` consumer. Minute alignment, the re-arm
  after each tick, the settle margin, the `focus`/`visibilitychange`/`pageshow` catch-up,
  refcounted start/stop, StrictMode's double subscribe, the stable snapshot identity. What
  happens across a DST transition, a clock set backwards, a tab throttled to one timer a
  minute, a `visibilitychange` that fires while hidden? Is `nowUtcIso` at millisecond
  precision a problem anywhere a minute-floored value was assumed?
- **The re-anchor effect** in `FixturesPage.tsx`: the URL is the pin test. Enumerate the
  cases — no `?date=`, `?date=<yesterday>`, `?date=<today>`, "Jump to today", Back/Forward
  across a rollover, the month view anchored to the 1st.
- **The workflow** — `sync.yml` line by line: exit-code capture under `-eo pipefail`, the
  `dry_run` input arriving as a string, `concurrency`, the force-push to `sync/scheduled`,
  the `gh pr list`/`edit`/`create` branch, the dispatched `verify` check, what a standings
  failure (non-fatal by design) looks like in the PR body, and what the first cron run will
  do the moment this merges. Permissions: is `actions: write` the minimum? Is anything in the
  body user-controlled text GitHub would render as markdown?
- **Absolute words in comments** ("never", "always", "cannot", "exactly") — each is an
  assertion to test.
- **Tests** — do the new ones test behavior or implementation? Is any data-honesty assertion
  weaker than before? Are the synthetic events honest stand-ins for ESPN's shape?

**Dynamic pass — mandatory, in a real browser.** Build, serve, and drive it: all 3 lenses ×
2 themes × 2 tabs at **360, 375, 390 and ~1000px**; set the viewport *before* any capture and
assert `document.documentElement.scrollWidth === window.innerWidth` on every screen. Re-run
the row-1 clock scenarios yourself — do not trust the PR body's account of them. The method
that worked last time: inject a `Date` subclass carrying an offset into the page through a
`<script>` element (so it runs in the page's world), import the app's clock module by the
exact URL Vite served it under (`performance.getEntriesByType('resource')` shows the `?t=`
suffix — a plain import gets a fresh, unsubscribed instance), and dispatch a `focus` event as
the catch-up signal. Also drive `sync.yml` once yourself:
`gh workflow run sync.yml --ref claude/kickoff-v0.2.0-time -f dry_run=true`, then read the
step log. A real (non-dry) dispatch against the branch opens a PR that inherits the whole
tree and shows CONFLICTING — expected; close it and say so.
