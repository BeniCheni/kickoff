## Verdict on feasibility (short)

**Feasible, and the right next tooling step.** Claude Code skills are Markdown files with a
front-matter header, loaded on demand when the user types `/name` or when the task matches
the skill's description. This repo already has everything a review skill needs written down —
`CLAUDE.md`'s verification discipline, the "Process notes" in `docs/v0.2.0-ideas.md`, and two
archived review prompts that share a structure. The skill is the step that stops re-typing
that structure per release and starts versioning it with the code.

What it buys, concretely:
- **The review method stops living in chat history.** Today the rules ("verify, don't vibe";
  the sealed appendix; the 360/375/390/1000 matrix; `scrollWidth === innerWidth` before any
  capture; never weaken a data-honesty assertion) are re-stated in every prompt. In a skill
  they are stated once and diffed like code.
- **The prompt ladder's step 4 becomes a command.** `/beni-pr-review 8` should produce the
  review session's opening move — spec lineage, method, fix policy, the landing steps — with
  only the PR-specific parts (number, branch, spec files, the sealed appendix) filled in.
- **It is teachable.** Building it is a compact tour of how Claude Code loads instructions:
  project vs user skills, front-matter, argument passing, when a skill fires by name vs by
  description, and how a skill can *call* other skills (`/code-review`, the browser tools).

What it does **not** buy: judgment. The skill encodes the method; the adversarial reading is
still the model's work in the session. A skill that tried to pre-list findings would be the
sealed-appendix anti-pattern in a new costume.

## What the skill should encode (draft outline of `SKILL.md`)

```markdown
---
name: beni-pr-review
description: Adversarial review-fix-merge pass for a Kickoff PR (Track B, ladder step 4). Use when asked to review, verify, or land a Kickoff pull request.
---

# Kickoff PR review — verify, don't vibe

Arguments: `$ARGUMENTS` = the PR number (required) and optionally `--no-merge`.

## Read first, in this order
1. `CLAUDE.md`, `AGENTS.md` (they outrank this skill on process).
2. The PR's spec lineage: `docs/v<X.Y.Z>-proposal.md` → design brief (if any) →
   implementation prompt (if any). Precedence: template > design brief > implementation
   prompt. Note every resolution in the PR conversation.
3. The full diff: `git diff main...<branch>` — every hunk, not a skim.

## Static pass — hunt these classes
- Data honesty (the house religion): postponed/cancelled wearing a dead time; TBC leaking a
  confident number; anything invented (minutes, matchday numbers, scheduledness).
- Time: every `new Date()` / `todayIso()` capture; anything that freezes at mount.
- URL & history, theme memory, a11y & AA on every new colour pair, motion budget.
- Absolute words in comments ("never", "always", "cannot") — each is an assertion to test.

## Dynamic pass — mandatory, real browser
- `npm run typecheck` and `npm test` on the branch head; report the real numbers.
- Every lens × theme × tab at 360, 375, 390 and ~1000px. Set the viewport *before* any
  capture; assert `document.documentElement.scrollWidth === window.innerWidth` on every
  screen. A pretty screenshot is a claim, not evidence.
- Whatever the PR's own verification matrix promised (read it out of the proposal): re-run
  the browser scenarios, do not trust the PR body's account of them.

## Fix policy
- Fix what you can reproduce, in scope; every behavioral fix gets a test where the logic is
  pure. No feature creep, no new dependencies, no silent token repaints.
- Never weaken a data-honesty assertion to make anything pass.
- Commits: small units, authored `Claude <noreply@anthropic.com>` via per-commit `git -c`;
  each message says what broke, how it was proved, how the fix was verified.

## Land it
1. Push fixes to the PR branch; wait for `verify`.
2. One PR comment: verdict, findings table (severity · finding · how verified · fix commit),
   what was deliberately not done, the browser matrix as run.
3. Squash-merge (unless `--no-merge`), message written as a release note in the repo's voice.
4. Tag if the PR is a release (`git tag -a vX.Y.Z`), pull `main`, confirm green.

## Sealed appendix
If the invoking prompt carries prior findings, treat them as suspicions to re-derive
independently, never as conclusions. A no-finding review of a large diff is a finding about
the review.
```

## The deep-dive session — step by step

1. **Where skills live and how they load.** Compare `~/.claude/skills/<name>/SKILL.md`
   (user-wide) with `.claude/skills/<name>/SKILL.md` (project, committed, visible to every
   session in the repo — the right home for this one, since the method belongs to the repo).
   Confirm with `ListSkills` inside a session that the skill appears once the file exists.
2. **Front-matter and triggering.** `name` becomes the slash command; `description` is what
   lets the skill fire without the slash when a request matches it. Write the description so
   "review PR 8" triggers it and "review my plan" does not.
3. **Arguments.** Use `$ARGUMENTS` for the PR number; decide whether `--no-merge` is worth
   supporting (it is: the v0.0.3 review merged, but a review of someone else's PR should not).
4. **Build it from the two archived prompts.** Diff `docs/v0.0.3-review-prompt.md` against
   `docs/v0.2.0-review-prompt.md`: what is identical is the skill body; what differs is the
   per-PR input (number, branch, spec files, appendix). That diff *is* the design.
5. **Test it on a closed PR first.** Run `/beni-pr-review 5 --no-merge` against the merged
   sync PR — a small, known-good diff — and check the session reads the right files, runs
   typecheck/tests, and produces the comment shape without posting it.
6. **Then on the real thing.** The next release's review (v0.2.1 or v0.3.0) runs through the
   skill; the archived `docs/v<X>-review-prompt.md` for that release becomes a two-line
   pointer ("run `/beni-pr-review N`; appendix below") instead of a full prompt.
7. **Retro (Track B Step 9).** Three things the skill got right, three to fix; fold the fixes
   into `SKILL.md` and, if the *method* changed, into `CLAUDE.md`.

## Open questions for that session

- Should the skill also *generate* the sealed appendix from a prior session's notes, or must
  a human always paste it? (Leaning: human — the seal is the point.)
- Does the skill call `/code-review` as a first pass, or is the built-in review's output too
  general for the data-honesty classes this repo cares about? Try both on PR #5.
- Where does the browser matrix script live — inline in the skill, or as a checked-in
  `scripts/verify-matrix.mjs` the skill runs? (Leaning: checked-in script; a skill should
  point at code, not contain it.)
