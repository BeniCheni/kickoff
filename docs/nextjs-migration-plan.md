## 2. The target architecture

### Framework and rendering decisions

Recommend **Next.js 16.4.0, App Router, Node runtime, npm and the existing Node 24 floor**, with the supported stable patch rechecked and pinned in N1. The docs read today show 16.4.0; 16.x is Active LTS and 15.x Maintenance LTS. Do not freeze this research date into a future unsupported version. App Router supplies server pages and route handlers while keeping the existing React components as client islands. [DOCUMENTED · read 2026-10-13: installation](https://nextjs.org/docs/app/getting-started/installation), [support policy](https://nextjs.org/support-policy). Exact Next/React/Tailwind/TypeScript compatibility is **UNVERIFIED**, U01.

Recommend initially leaving **Cache Components disabled explicitly** and using the documented previous-model `unstable_cache` API for catalog data, not layering the new partial-prefetch model onto the migration. That API is still documented but Next recommends `use cache` for Cache Components. This is a deliberate transitional cost: one future caching upgrade after parity, with no extra cache service now. [DOCUMENTED · read 2026-10-13: database-query caching and lifetime](https://nextjs.org/docs/app/api-reference/functions/unstable_cache), [previous caching model](https://nextjs.org/docs/app/guides/caching-without-cache-components). In particular, do not assume ordinary `use cache` is durable across serverless requests; the current docs distinguish in-memory runtime results from remote caching. [DOCUMENTED · read 2026-10-13: caching](https://nextjs.org/docs/app/getting-started/caching).

Use a single public `/` page, preserving the query-tab contract. It awaits request search parameters and renders the chosen surface; `/privacy` is the separate legal route. There is **no invented `/moments/<id>` migration**. Server `searchParams` makes a page dynamic; `connection()` can also explicitly defer work until a request. [DOCUMENTED · read 2026-10-13: page props](https://nextjs.org/docs/app/api-reference/file-conventions/page), [connection](https://nextjs.org/docs/app/api-reference/functions/connection).

Rendering by surface, including the shared-route implication:

- **Fixtures at `/` or `?tab=fixtures`: dynamic HTML, immutable committed JSON per deployment.** The data requires no database/network read or time-based ISR. Request rendering is for the query and request-time clock, not fresher fixtures. The client owns ongoing clock ticks and interaction.
- **Table at `/?tab=table`: dynamic HTML, immutable committed standings/fixture JSON per deployment.** Same reason; no change to rank authority, zones, layout or derived arithmetic.
- **Shell on `/`: static structure and assets inside a dynamic response.** Version/count/stamp come from the deployed commit. Do not label the whole route static merely because those inputs are static. No full-route/CDN HTML cache for `/`; query and clock must not be shared incorrectly.
- **Gallery at `/?tab=moments`: dynamic HTML using a server Drizzle catalog read with tagged, revalidated data.** Do not read the database during `next build`. Gallery list results can be cached independently of request HTML.
- **Watch at `/?tab=moments&watch=<id>`: dynamic HTML, tagged catalog metadata plus a fresh publication-eligibility check at entry and before loading a new clip.** Unknown/withdrawn returns the designed not-found surface; database failure returns unavailable, never a fabricated empty catalog. Metadata can share the list cache; the small eligibility read is deliberately uncached so a withdrawn clip cannot start from an old browser/RSC payload. D7 keeps one 16:9 player box with containment/bars for non-16:9 video; Q22 applies the record frame to thumbnail boxes, not a new watch-player ratio (D7 §6:205).
- **`/privacy`: static at build, rebuilt when audited copy changes.** It needs no database, live clock or visitor identity. It shares the pre-paint theme bootstrap and shell foot. The foot carries the complete query into /privacy, and its return link preserves that query; browser Back preserves the original full URL and fragment. No extra browser-storage key or server cookie is needed.

Fixtures/Table's existing data and visual behavior remain the parity baseline. The only requested addition there is the global Privacy & terms link (carried A-07); the framework port is implementation work, not product redesign. R(src/lib/fixtures.ts:4–17); R(src/lib/standings.ts:1–18); R(src/lib/lens.ts:1–9). D7 §1:61,78 and §3:103 carry that foot.

### Honest time through server rendering and hydration

Do not server-import the existing global browser clock or run `window`/storage initializers. Create a **request-scoped clock snapshot** from one `Date.now()` after the request boundary, floor it to the minute by the existing rule, and serialize `{nowUtcIso, today}` to the client provider. `today` always uses the existing explicit `America/New_York` formatter. All SSR selectors on that request use the same snapshot. R(src/lib/clock.ts:42–52); R(src/lib/time.ts:32–59,99–108). Server time is render time, not a claim that the reader's tab received the response in that minute.

Add the third `useSyncExternalStore` server-snapshot argument. Both SSR and the first hydration render return the identical serialized object; after subscription, the browser store immediately samples its own `Date.now()`, then resumes minute alignment and focus/visibility/pageshow catch-up. Use a provider/client store per mounted app, never a shared server singleton. This preserves the reader-clock semantics already used by Kickoff, and handles transport across Brooklyn midnight without mismatched initial HTML. If the client's clock is badly wrong, Kickoff still cannot certify real time; that pre-existing limitation must be measured in the skew test, not hidden with hydration-warning suppression. R(src/lib/useNow.ts:8–10); R(src/lib/clock.ts:88–113,134–152). Mechanism is **PROPOSED**, U01.

Default `date` is the serialized request's Brooklyn today during hydration, then tracks browser today only while no `date` parameter is pinned. Carry `canonicalSearch`'s once-per-load behavior; do not canonicalize every tick or turn an explicit date into a server-zone instant. R(src/lib/urlCodecs.ts:46–65); R(src/components/FixturesPage.tsx:26–43). Preserve stored `timeConfidence` and existing TBC/error behavior; never use SSR to infer a league's missing kickoff. R(AGENTS.md:13–15); R(src/components/TablePage.tsx:459–463).

Freshness uses **the committed `META.lastSyncAt`**, not request time, deployment time, a catalog fetch, or a generated clip's date. Header `SYNC_STAMP` remains the UTC provenance instant; `LAST_SYNC_DATE` remains Brooklyn-local. `StalenessBanner` computes elapsed hours from the shared clock: absent below 24, advisory from 24, stale from 72, with current copy. Twenty hours is the sync's quiet-refresh publication threshold, **not** the banner threshold or a promise of an update every 20 hours. R(src/lib/fixtures.ts:126–138); R(src/components/StalenessBanner.tsx:10–25); R(CLAUDE.md:144–157).

N2 must prove same initial snapshot on server/client, immediate browser catch-up across minute/midnight, DST mismatch week, unpinned versus pinned date, exact/TBC kickoff, 23:59→24:00 and 71:59→72:00 freshness boundaries, hidden return, bfcache and StrictMode cleanup. ### Publication, withdrawal and cache visibility

Use one server-only catalog access layer returning validated public DTOs. It holds Drizzle and the login string; client imports must fail the build. The browser sees public catalog fields and Storage URLs only. [DOCUMENTED · read 2026-10-13: server-only DAL and minimal DTOs](https://nextjs.org/docs/app/guides/data-security). Publication continues to be the Studio's database write, never an app action or edition PR. The thumbnail-only PR is separate.

Recommend **on-demand tag invalidation from the local Studio**, rather than waiting for the next fixture deployment or ordinary TTL. Proposed list/metadata tag: `kickoff-catalog-v1`; keys include schema/DTO version and id, never lens/theme or arbitrary unknown URL parameters. Give cached catalog reads a 60-second revalidation backstop; that backstop is not the live-publication guarantee. Cache rows together with their actual successful-read timestamp. If the wrapper receives a cached result older than 60 seconds, it must await an uncached read and render unavailable on failure, rather than let a failed background revalidation serve old rows indefinitely. This bounded-age mechanism needs U02 proof; it must not reuse the fixture sync stamp or invent a media date. At Publish/Unpublish commit, record a durable Studio delivery event in the same database transaction, then POST to the production app's `/api/catalog/revalidate`. The handler invalidates the list and relevant detail tags with `revalidateTag(tag, {expire: 0})`, so the next server read blocks for fresh data. Do **not** use the stale-while-revalidate `"max"` profile for this promise. [DOCUMENTED · read 2026-10-13: immediate expiry versus stale revalidation](https://nextjs.org/docs/app/api-reference/functions/revalidateTag).

Beni creates **`CATALOG_REVALIDATE_SECRET`**, an independent random secret held in his outside-repo Studio env file and the Vercel **Production-only** server environment. Never `NEXT_PUBLIC_*`, never in a query string, never the database password. Authenticate a bounded POST body with HMAC, operation/id/revision and a short signed timestamp; validate content before fixed-tag invalidation, use constant-time comparison, rate-limit failures, redact the signature and return minimal results. Retries sign a fresh timestamp for the same delivery id. The Studio event queue owns retries; the read-only app never writes Studio state.

After invalidation, Studio verifies through a fresh same-origin catalog read that the row appears/vanishes before reporting **reader delivery confirmed**. Fallback states separately say PR pending, merged/deploy pending, then serving, as D7 requires (§0:22; §9:240–247). Missing invalidation acknowledgement is **published/withdrawn in the database, reader delivery unconfirmed**; do not retry the database mutation, fabricate success, or tie catalog visibility to the fallback PR. A committed withdrawal still blocks new watch starts through the uncached eligibility read.

“Live at once” has a distributed-system limit: a DB transaction and a remote cache invalidation cannot be one atomic event. This mechanism removes deliberate cache delay after successful delivery and verifies it; it cannot promise zero network propagation time, recall an already-loaded media file, or synchronously update every open tab. D7 already discloses the inability to recall an open/cached file (§3 Unpublish). **U02 is a cutover blocker**: if PM's interpretation demands fresh gallery reads at the exact record boundary even when delivery fails, use uncached dynamic gallery reads in production until the stronger invalidation guarantee is demonstrated. The pivot is settled; the unresolved item is an operational proof/copy precision, not whether publishing stays in the database.

Prevent stale client navigation from defeating this: disable prefetch for catalog-changing entry links initially, refresh the catalog on Moments entry and visibility return, and check eligibility again on Play/Up next/autoplay advancement. An already-open gallery refreshes on return/manual retry; continuous instant fan-out is not claimed. No browser database subscription is introduced. Proposed fault tests cover duplicate/out-of-order events, bad secret, write success plus lost acknowledgement, concurrent cache misses, Unpublish between metadata read and Play, stale browser history, paused DB and deployment change during invalidation.
