## Implementation decisions

- `RESULT_CHANGED` compares two present scores. Ordinary completion is already
  `STATUS_CHANGED`; it does not produce a second correction line. A correction is urgent
  at any horizon, since the inherited minus-six-hour tail misses older settled results.
- `TEAM_RENAMED` is never urgent and is deduplicated per competition, stable team identity
  and before/after name pair. Without a provider identity, fixture-level evidence is kept.
  `TEAM_CHANGED` reports a provider identity change, including loss/addition of identity,
  as urgent at any horizon. Swaps are recognised by ids when both are known, with a name
  fallback otherwise, and do not become two misleading rename lines. Counts fold into
  the existing report grammar; no fields are reordered or added.
- Every successful real run takes the same validation, snapshot PR, held-check approval
  and CI-gated merge path, with the merge request pinned to this run's generated head. `changed=false` retains its literal meaning; it now publishes
  verified freshness when standings are unchanged. Legacy `standings=failed`, malformed
  reports and unexpected exit codes fail closed. Dry runs publish nothing.
- One rolling `sync/scheduled` branch remains sufficient: there is no human-held
  change-bearing branch to collide with, the premise behind the older `sync/quiet`
  suggestion. The whole generated fixture/meta/standings boundary is staged even on quiet
  checks. Staging just the two top-level stamps can mismatch fixture counts when the
  rolling window expires rows; the accepted cost is per-fixture fetchedAt churn in Git.
  Quiet commits are named `sync: verified unchanged`, and every snapshot commit carries
  the full report line. No snapshot is hand-edited.
- `docs/sync-digest.md` is generated in the same snapshot PR only when the report changes.
  It is published on main exactly when its snapshot merges. Retention is the newest 30
  change-bearing runs, up to 400 lines / 32,000 characters each, with full Actions-log
  links. Older entries remain in Git history; Actions logs follow repository retention.
  This avoids a separate issue writer, additional token permissions and a post-merge
  digest race. Indented provider text cannot close a Markdown fence or forge an entry.
  The digest is a reading aid, never a claim that a person acknowledged a change.
- Bot-token pushes do not trigger Pages. The sync observes its expected PR head merge,
  then explicitly dispatches `pages.yml` on main if its latest successful run is behind.
  The existing `actions: write` permission suffices. A changed head, closed PR, ten-minute
  merge timeout or rejected dispatch fails visibly. The next real sync attempts recovery
  of earlier main delivery before fetching; a recovery failure alone does not block the
  fresh fetch. Dispatch requests delivery, but does not prove it completed. No new
  schedule, dependency, secret or authentication setting is introduced.
- Real workflow publication is restricted to main. Feature-branch verification uses the
  existing `workflow_dispatch` with `dry_run=true` and cannot push, digest or deploy.

The Pages mechanism follows GitHub's documented
[bot-token trigger exceptions](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow):
an explicit workflow dispatch can start another workflow using the existing token.

## Verification and release acceptance

The local regression suite executes the workflow's actual report-reader shell against
clean, urgent, legacy-failed, malformed, missing and killed-process outputs. Isolated gh
stubs exercise the deployment scripts for merged/closed/pending PRs, changed heads,
already-deployed main, invalid main identity and failed dispatch. Pure tests cover the
new diff kinds, rename deduplication, swap identity, digest retention, bounded excerpts
and hostile provider text. Existing snapshot-honesty tests remain intact.

Before the PR is ready for cold review: typecheck, full tests and production build; a
390 px and 1000 px browser smoke with header version/count and document width equality;
the PR's pull_request verify at the exact tip; a dry-run sync dispatch on the feature
branch. The browser checks exercise the unchanged app; no fixture JSON is mutated.

Only after merge can the changed workflow prove real quiet publication and delivery.
Observe a successful quiet run creating its named PR, verify at that PR's exact head,
the merge, a successful Pages run and the live header's fresh stamp/count. Observe a
change-bearing run publishing a digest entry with its snapshot. Dry-run CI and mocked
gh cannot establish either live integration result. Beni owns the release merge/tag;
the builder must not substitute its own review for Claude's cold pass.
