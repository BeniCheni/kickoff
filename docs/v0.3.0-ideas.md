# v0.3.0 — candidate work, from the v0.2.0 review

Written cold, 2 Sep 2026, by the session that reviewed and landed PR #8 (v0.2.0, "the app
learns to tell time"), for whoever scopes the next release. Everything here was judged
*real* during that review and *out of scope* there — either carried open from
`docs/v0.2.0-ideas.md` (rows 2, 4–9, 11, 12 stay open; their text there is still the
fuller description) or found by this pass. Ranked by research value × feasibility; sizes
are rough (XS < an hour, S < half a day, M ≈ a day or two).

Two things about v0.2.0 shape this list. First, the scheduled sync now commits only when
the diff engine reports a change, so on a quiet stretch the app's `synced` stamp and the
staleness banner measure time since the last *change-bearing* sync a human merged — they go
amber at 24 h and red at 72 h through an international break even though the bot verified
nothing moved, twice a day. That is a known, accepted, documented price (proposal, "Review
resolutions"), and rows 1–2 below are how it gets paid off. Second, every browser-found bug
in two releases running has lived exactly where the unit tests stop (the component wiring),
which is why row 5 keeps its place.

## Ranked ideas

| # | Idea | Why it matters | Size |
|---|------|----------------|------|
| 1 | **The diff engine's two blind spots: result corrections and team-name changes.** `diffFixtures` compares kickoff, status, venue, roles and time confidence — not `result`, and not `home.name`/`away.name` when the `sourceId` is unchanged. A corrected full-time score (ESPN does amend own-goals and late VAR reversals) or a club rename lands in the snapshot with no report line. Add `RESULT_CHANGED` and `TEAM_RENAMED` kinds (never urgent for a rename; urgent for a result inside the horizon), with tests. | The diff engine is the whole safety story, and "no changes" must mean no changes before anything is built on it — row 2 depends on it. | S |
| 2 | **Auto-merge an *empty* sync report.** Once row 1 lands, a run whose report line is `changed=false` is a verified statement that nothing moved — and the only thing the human review of a data PR protects is the change list. Let the workflow, on `changed=false`, commit the stamp-only refresh and squash-merge it itself (`gh pr merge --squash --auto` after the dispatched `verify` is green; the CI-gate ruleset still applies), so `lastSyncAt` advances and the banner stays quiet through a break. Change-bearing runs keep the human. Argued in the proposal as the seam; this row is the work. | Pays off the v0.2.0 price without touching the no-auto-merge decision for changes. | M |
| 3 | **Poster's Tonight's slate and Ledger's Next-up now disagree *live*, once a minute.** `TonightSlate` filters by status and Brooklyn date and never reads `nowUtcIso`, so a `scheduled` fixture stays in "N REMAINING" after its exact kickoff has passed; `NextUpStrip` (via `upcoming`) drops it at the kickoff minute. Pre-existing, but v0.2.0's ticking clock makes the two heroes contradict each other in real time on every match night. ## Process notes — what this review taught about verifying a PR

Added to the v0.2.0 list, which still applies (screenshot the whole matrix; assert, don't
admire; 390 is the judge, 360 the jury; absolute words are review bait; test past the
module boundary; latent paths need synthetic data; the hidden-tab transition gotcha).

- **Read the previous run's log before believing a workflow step is reachable.** The
  "Nothing changed" step was unreachable in the shipped `sync.yml`; the proof was the 1 Sep
  dispatch's own log — "no changes" followed by "961 insertions(+), 961 deletions(-)" and a
  PR. A workflow's branches are verified by reading step outputs from a real run, not by
  reading YAML. A `dry_run` dispatch is the workflow's unit test; use it after every change.
- **A test named for a claim must exercise the claim.** "A visibility tick in the same
  minute is a no-op" passed without ever moving the fake clock, so it tested "no time
  passed", not "same minute". Strengthening it to jump 23 s failed on the unfixed store. When
  a comment makes an assertion, the test should be able to fail it.
- **Every `console.warn`-and-continue in an unattended script is a silent path.** Grep
  `scripts/` for `warn` at review time and ask, for each, what a reader who never sees the
  console would want. Three of four became exit 2 across v0.2.0 and its review.
- **Driving the clock in a real browser, the method that works:** inject a `Date` subclass
  carrying an offset through a `<script>` element (page world), `import()` the app's clock
  module by the exact URL Vite served it under (`performance.getEntriesByType('resource')`;
  check `subscriberCount() > 0` to prove you hold the app's instance, not a fresh one),
  set the offset, dispatch `focus` as the catch-up signal. Exercise URL state with
  `history.replaceState` + a synthetic `PopStateEvent` instead of navigating, so the shim
  survives.
- **The Browser pane can be hidden while your script runs, and `requestAnimationFrame`
  never fires in a hidden document.** A wait built on rAF hangs to the tool's timeout and
  looks like a stuck renderer. Settle React with `MessageChannel` ticks (its own scheduler
  primitive, unthrottled) and measure with `scrollWidth`, which lays out on demand whether
  or not anything paints.
- **The merge box counts only the PR's own event runs.** A `workflow_dispatch` check-run on
  the head SHA — attached, green, associated with the PR in the REST API — never appears in
  `statusCheckRollup` and never unblocks the merge (PR #7, PR #9 twice). The bot's PR does
  trigger `pull_request`, GitHub just holds the run for approval; the fork-PR approval policy
  setting made no difference; approving the held run through the Actions API with the
  workflow's own token works in thirty seconds. Test the merge box itself, hands off, before
  believing any theory about check-runs — the first theory shipped (PR #10) was wrong.
- **A machine-readable line beats parsed prose, and the line's format is an API.** Pin it
  verbatim in a test, validate it with the same regex in the workflow, and fail loudly when
  it is missing — never fall through to a guess.
- **Name the consequence of a fix in the spec of record.** Gating commits on the report
  changed what the staleness banner means; the proposal and `CLAUDE.md` say so, and this
  list carries the follow-up. A fix whose side effect is undocumented is half a fix.
