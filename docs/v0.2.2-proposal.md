## Audit — where the brief and the repo disagree

The brief was written against `5e0b76d` and the repo is at `5e0b76d`; nothing it cites is
stale. Two refinements from the read:

- **`TonightSlate` counts `in_play` fixtures as remaining today** (`TonightSlate.tsx:32`). The
  brief describes the gap as "a `scheduled` fixture stays after its kickoff"; it is wider — a
  snapshot `in_play` fixture has kicked off by definition and is still inside "N REMAINING".
  Under the settled semantics (remaining = not yet kicked off) it leaves too. Named under B.
- **Three of three real scheduled runs fired late by more than the new interval**: 2 Sep
  19:14Z (scheduled 16:00Z, +3 h 14 min), 3 Sep 08:35Z (04:00Z, +4 h 35 min), 3 Sep 19:08Z
  (16:00Z, +3 h 08 min); the 4 Sep 04:00Z run had not fired at 05:50Z when this was written.
  GitHub's own docs name the start of every hour as the high-load window and say to schedule at
  a different minute. That changes the cron recommendation — see C1.

Everything else the brief asserts about line numbers, the `changed=false` gate, `base: './'`,
the two theme keys and the `Default` ruleset (id 21894544, still active, still empty) was
re-read and holds.

## A — Poster becomes the default lens

What moves: `src/lib/lens.ts` (the fallback, the omission, the doc comment — which said "Ledger
is the default" twice), `src/App.tsx:31`'s default argument, `tests/lens.test.ts` (every
assertion in "omits the default" and "falls back on junk input", plus a new round-trip test that
`?lens=ledger` survives encode → decode, since Ledger is now the value that must be written
down), and the README lens table. `src/main.tsx`'s pre-paint bootstrap reads `parseLens` and
follows with no edit; the verification matrix watches its first frame anyway, because a
wrong-lens flash is the exact thing that code exists to prevent.

What looks like work and is not, confirmed:

- **Theme defaults do not move.** `resolveTheme` forces dark only for Broadcast; Poster shares
  the `kickoff-theme` key with Ledger, so the default theme stays "stored choice, else
  `prefers-color-scheme`". Nothing in `theme.ts` changes behaviourally.
- **`themeStorageKey('ledger')` at `theme.ts:72`** means the shared non-Broadcast key, not
  "Ledger's key", and reads oddly once Ledger is no longer the default. It gets a one-line
  comment. The storage key itself is not renamed — that would silently drop every existing
  reader's stored theme.

Decisions:

1. **Pill order stays `['ledger', 'poster', 'broadcast']`.** `LENSES` drives the switcher's
   reading order and its arrow-key / Home / End contract, and the order is a loudness gradient
   (quiet → loud). Poster simply starts filled. Reordering for "default first" would break the
   gradient and rewire the keyboard contract for a cosmetic win.
2. **No normalize-on-load.** Stripping a redundant `?lens=poster` from the address bar is row
   7's `canonicalSearch()` work, in v0.2.4 with the rest of `useUrlState`. Not half-built here.
3. **URL back-compat is an accepted cost.** Every previously shared link without `?lens=` now
   opens Poster. Sole user, so the blast radius is Beni's own bookmarks — but a URL that
   silently changes meaning is the kind of thing this repo writes down. It is in the CHANGELOG.

## B — Poster's hero stops contradicting Ledger's

The honesty item, and the reason A is defensible: promoting Poster to the front door promotes a
hero that lies about time once a minute. `TonightSlate` takes `today` and `active` and never
reads a clock; it filters by `status`, so a `scheduled` fixture stays inside "N REMAINING"
(`slateSubLine`) after its kickoff has passed, and a snapshot `in_play` fixture is counted as
remaining from the start. `NextUpStrip` reads `useNow()` and calls `upcoming(today, nowUtcIso,
…)`, which drops a fixture at its kickoff minute. Since v0.2.0's ticking clock the two heroes
contradict each other live on every match night — `docs/v0.3.0-ideas.md` row 3.

The semantics were settled by the Poster template and recorded in `docs/v0.2.1-proposal.md`
§"Deferred, and why": **remaining = not yet kicked off.** This release ships the implementation
half only:

- One pure gate, `stillToKickOff(fixture, nowUtcIso)` in `src/lib/fixtures.ts`: `scheduled`,
  and a league-set time still ahead of `nowUtcIso` — a placeholder (TBC) time is trusted only
  to the day and is never evicted by arithmetic it never claimed. `upcoming` is rewritten over
  it, so the two heroes share one gate rather than two copies of one.
- One pure planner, `planSlate(today, nowUtcIso, active, fixtures)` in `src/lib/fixtures.ts`,
  returning `{ date, slate, isTonight }` — tonight's still-to-kick-off fixtures, else the next
  matchday's scheduled ones. `nextMatchday` gains an injectable fixture list so the planner is
  testable on fabricated data. `TonightSlate` reads `useNow()` and renders what the planner
  returns; nothing about time is decided in the component.
- Consequences, named: a fixture leaves "N REMAINING" at its kickoff minute, in the same tick
  `NextUpStrip` drops it; the "Next matchday — nothing left today" flip fires at the last
  kickoff instead of at the next snapshot; a snapshot `in_play` fixture is no longer
  "remaining". Row 13's note that `N REMAINING` counts TBC fixtures the FIRST/LAST range
  excludes is unchanged and still open.

Out of scope, unchanged: row 4's stale-LIVE pill on `FixtureRow`. That needs a designed state
("kicked off, outcome unknown to this snapshot"), and a pill invented in a build prompt sits at
the bottom of the precedence ladder. It waits for the design cycle.

## C — The sync stops knocking

Beni's ask was "auto-merge the sync PRs"; the scoped version is **hold only what a human must
read.** Three changes: cadence (`sync.yml`), the merge verdict (`scripts/diff.ts`,
`scripts/sync.ts`, `sync.yml`), and the cross-track contract (`CLAUDE.md`).

**C1 — cadence.** From twice a day to every three hours (8×/day), Beni's call. Cron
`23 1,4,7,10,13,16,19,22 * * *` — the brief recommended `0 1,4,…`, and the hours are kept:
midnight and noon ET stay in the set, so the workflow's DST paragraph stays true (rewritten,
since it argued for exactly two runs and named their purpose). **The minute is overruled**,
with the reason above: GitHub's docs name the top of the hour as the high-load window and
advise another minute, and every real scheduled run so far has been 3–4½ hours late. `:23` is
a hypothesis, not a fix — the first 24 hours of delivery times go in the PR conversation, and
"What stays unverified" carries it.

Honesty constraint on the copy: the README and CHANGELOG say what is *scheduled*, never what
is guaranteed. An 8×/day schedule under 3-hour delays may deliver fewer runs and they may
bunch. "Every three hours" as a promise would be the confident lie this repo is named after.

**C2 — the verdict.** Decided in TypeScript, unit-tested, printed; the workflow only obeys it.
`mergeVerdict(changes, standings)` in `scripts/diff.ts` returns `hold` with a reason list when
any of:

- `urgent > 0` — a change inside −6 h..+72 h of now, or a `STATUS_CHANGED` to postponed or
  cancelled at any horizon (the existing `isUrgent` and `hasUrgentChanges` rules, unchanged);
- any `DISAPPEARED` or `HOME_AWAY_INVERTED` change of any horizon — a vanished fixture and an
  inverted moneyline are the two that cost money far out;
- `standings=failed` — the previous table was kept; a human should know the report is partial;

and `auto` otherwise. The report line gains one field at its end — `merge=auto|hold` — so it
reads `report: changed=… changes=N urgent=N standings=… rank-moves=N merge=…`. The format is
pinned verbatim in `tests/diff.test.ts`; `sync.yml`'s regex is extended to match it exactly and
still fails the job when the line is missing or malformed. `merge=` is a verdict about the PR
this run would open; on a `changed=false` run it is printed and nothing reads it. The hold
reasons are printed as their own lines above the report so the PR body says *why* it is held.

**C3 — a held PR stays held (sticky hold).** The rolling branch is force-pushed from a fresh
checkout of `main` every run, so each run's report is cumulative against `main` — but urgency
expires (`isUrgent` is false once a kickoff is more than six hours past), so an urgent change
Beni never read can age out and be swept into a later run's auto-merge. Mechanism: **a label,
`hold: human`.** A run whose verdict is `hold` adds it (creating it on first use) and runs
`gh pr merge --disable-auto`, so an auto-merge armed by an earlier run cannot fire on the new
changes. A run whose verdict is `auto` refuses to arm auto-merge while the label is present,
whatever the current verdict, and says so in the step summary. The label is cleared only by the
human merge (the PR closes; the next PR is fresh) or by Beni removing it. Chosen over a body
marker because the body is rewritten every run and a label survives that, is visible in the PR
list, and is a one-click human override.

*Accepted cost, named:* **aged-out urgency on a held PR is still merged by a human**, never by
the bot — but a change that was urgent on Tuesday and expired by Friday is presented to Beni on
Friday as a non-urgent line in a held PR. The label tells him the PR was flagged; it does not
tell him which line did the flagging. The PR body carries the reasons from the *latest* run
only. Reading the run history is the recourse. Not fixed here.

**C4 — mechanics.** After the existing "Approve the PR's held verify run" step: on `auto` with
no label, `gh pr merge <N> --squash --auto --subject "<title>" --body "<report line>"`, so
GitHub merges once the required `verify` check is green. If `--auto` is refused (the repo's
"Allow auto-merge" is off today — Beni's click), the step warns and leaves the PR open; it never
falls back to a blind immediate merge. The rulesets still gate the merge box; the force-push
behaviour and the `concurrency` group are unchanged (§"Open decisions"). Permissions gain
`issues: write`, for the label. The squash commit of an auto-merged PR is authored by
`github-actions[bot]`, which is what already authors the branch commit; the human-merged ones
stay authored by the merger.

**C5 — the cross-track consequence.** `CLAUDE.md`'s "Scheduled sync" section and the PR
body's reviewer checklist encode a contract with the betting pipeline: *every sync PR is a
Step 0 re-verification trigger.* After this release the contract is: **every sync PR left open
for you is a Step 0 trigger; the ones that merged themselves carried nothing inside 72 hours,
nothing that vanished and nothing inverted.** `CLAUDE.md` is rewritten in the same commit; the
CHANGELOG says it; the PM carries it into `/beni-betting-pipeline`'s Step 0.

**C6 — what this does not fix, plainly.** More frequent syncing does not quiet the staleness
banner during an international break. A run whose diff engine reports nothing still commits
nothing (v0.2.0's gate), so the banner keeps measuring time since the last change-bearing
merged sync and goes amber at 24 h and red at 72 h through a quiet stretch. That is v0.2.0's
named accepted cost; row 2's `changed=false` stamp-only commit and row 1's blind spots pay it
off, and they stay in v0.3.0. The `StalenessBanner` thresholds are not touched: while the
banner measures change-bearing syncs, tightening them makes it louder during breaks, not
quieter. Row 1 is not a prerequisite for the urgency gate — a result correction or a rename is
invisible to the diff engine today whether or not the PR auto-merges, so this release does not
widen that hole. It *is* a prerequisite for row 2, where "nothing changed" has to mean it.
