## The approved boundary and its cost

**A fixture or standings fetch/validation failure aborts the sync with exit 2 before any
snapshot writes.** Fixtures and standings form v0.2.5's authoritative snapshot boundary;
metadata describes that same successful fetch. Fetch and validate both before publication.
If either fails, publish neither. Committed data remains the last completely successful
authoritative snapshot rather than a partially advanced state.

A standings outage can intentionally delay otherwise valid fixture updates. This is an
accepted availability cost of atomic publication of the fixtures + standings authoritative
snapshot, not an accidental side effect. Atomicity applies to this explicitly defined
boundary: future injuries, odds, weather, broadcast or other ancillary datasets do not
inherit membership automatically. Their semantics and failure consequences need a separate
decision. This supersedes the standings soft-failure exception introduced before v0.2.5.

The machine-readable report line keeps its existing shape. A refused fetch has exit 2 and
diagnostics, not a successful report; the workflow already treats that as a hard failure.
The `standings=failed` report variant remains accepted for compatibility with earlier runs.

## Evidence and accepted implementation details

**Row 8 implementation:** `runSync()` is the CLI's tested exit-code boundary. Both providers
reject un-normalizable entries, with competition, available identity, entry position and
reason; standings awaits all five results to retain all league diagnostics. Empty schedule
arrays remain valid, but a missing/non-array `events` field is a malformed fetch response.
Provider identity is checked before coercion/deduplication, with a schema backstop against
empty and coerced missing IDs. Missing time-confidence flags and score coercion are unchanged.

Both datasets and metadata are validated, then all three payloads serialized, before the
first write. Publication is the workflow's single Git commit of those files. This is not a
multi-file filesystem transaction: a disk/process failure during local writes can leave a
partial working tree, but a failed run is not committed. The fetch/validation failure
invariant is stronger: no snapshot write has begun. No new storage format or dependency.

Integration tests intercept filesystem writes while invoking the real orchestration: either
provider failing, either schema rejecting, waiting for standings, successful complete writes,
and `--check`. A subprocess also pins the actual CLI's exit 2 on an offline provider.

**CONFIRMED baseline:** Node 24.15.0; `npm run typecheck` passed; `npm test` passed 176 tests
in 17 files (node 153/11, dom 23/6); `tsc -p tsconfig.node.json` passed independently.
Initial runs lacked the locked jsdom/Testing Library installation; `npm ci` restored it
without changing either manifest. Local/remote main agreed; v0.2.4's missing tag was the
acknowledged owner release act, not a numbering change.
