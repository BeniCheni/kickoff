## The approved boundary and its cost

**A fixture or standings fetch/validation failure aborts the sync with exit 2 before any
snapshot writes.** Fixtures and standings form v0.2.5's authoritative snapshot boundary;
metadata describes that same successful fetch. Fetch and validate both before publication.
If either fails, publish neither. Committed data remains the last completely successful
authoritative snapshot rather than a partially advanced state.

A standings outage can intentionally delay otherwise valid fixture updates. This is an
accepted availability cost of atomic publication of the fixtures + standings authoritative
snapshot, not an accidental side effect. Atomicity applies to this explicitly defined
boundary: future injuries, odds, weather, broadcast or other ancillary datasets do not
inherit membership automatically. Their semantics and failure consequences need a separate
decision. This supersedes the standings soft-failure exception introduced before v0.2.5.

The machine-readable report line keeps its existing shape. A refused fetch has exit 2 and
diagnostics, not a successful report; the workflow already treats that as a hard failure.
The `standings=failed` report variant remains accepted for compatibility with earlier runs.

**Additional operational cost, identified in review:** a failed run neither creates nor
updates the sync PR that Track A Step 0 reads. An existing PR may still describe an older
successful fetch. Re-reading the unchanged app does not detect withheld fixture changes;
the age banner is absent before 24 hours and never identifies failed checks. A later
successful run is not guaranteed to reconstruct intermediate moves or hold a change whose
urgency expired during the outage. Publication also waits for a change-bearing merge.
The build accepted delayed publication but omitted this loss of the review trigger. Pass 2
accepts the finding and recommends a release gate on an explicit failure reader, pending
Beni's adjudication; it does **not** treat the row 15 deferral as sufficient acceptance.

### Pass 2 — Codex rebuttal, 5 Sep 2026

Reviewed the PR comment, this section, `docs/v0.2.6-ideas.md` rows 15–16 and its process
notes, then `9307803..335d4f8`. The two Claude commits remain in history. The corrections
below are Codex's conclusions, not a claim that the reviewer agreed to them.

**Failure visibility — accept medium, contest “fixed”; recommend a merge block.** The build
record explicitly accounts for exit 2 and delayed fixture publication. It does not account
for withdrawing Step 0's held-PR trigger. I missed that operational consequence; I should
have put it in the accepted-costs section before calling the boundary complete. That section
now names it. `CLAUDE.md` is the right home for the operator contract and `docs/HONESTY.md`
for the limits of the product's claims, but their added sentences were too reassuring.
Re-reading an unchanged snapshot cannot detect a move that never reached it. A timestamp or
an age banner cannot report a failed check; no banner renders before 24 hours. “Until the
next successful run” also overstates recovery: quiet runs do not publish, held PRs await a
merge, and intermediate changes need not survive the next fetch. Existing PRs and labels
are unchanged, not deleted by the failing run. The old soft-failure opened/held a PR only
when there was a fixture change; the failure alone was not a reason to commit.

The regression extends beyond delayed notification. A synthetic fixture moved from
`2026-09-06T18:00Z` to `19:00Z`: the real `diffFixtures` / `mergeVerdict` returned
`TIME_CHANGED, urgent=true, hold` at `2026-09-05T12:00Z`, then
`TIME_CHANGED, urgent=false, auto` at `2026-09-07T02:00Z`. A standings failure at the first
run prevents the PR/label that would have kept that change held. This is a reproducible
policy consequence, not a report of a live missed fixture. Existing integration tests also
confirm either fetch failure returns 2, writes nothing and emits no report; the workflow's
hard-failure step prevents subsequent publication steps. Fixture diffs can already be in
that run's console before standings fails, but the PR reader does not receive them.

I retain the atomic boundary. It needs an operational failure surface **in this release**,
not necessarily an app component: an owned delivery route covering runs with and without an
open PR, or Beni's explicit adoption of an Actions check before every Step 0 with independent
fixture re-verification after failure. Neither is established by this patch or by an ideas
row. My recommendation is to block merge until that reader is assigned and the procedure or
delivery is verified; Beni may adjudicate the residual cost explicitly. No new workflow,
notification subscription, issue or bot-PR action is silently introduced by this rebuttal.
`docs/v0.2.6-ideas.md` row 15 records this contested release gate, not a settled deferral.

**Charset — accept low; correct the test and the rationale.** Both fresh builds have a
648-byte bootstrap starting at byte offset 46 and a charset declaration ending after byte
763 (exclusive offset), leaving 261 bytes. The declaration must fit completely within
1024 bytes ([HTML Standard, encoding declarations](https://html.spec.whatwg.org/multipage/semantics.html#charset)).
The review's test really goes red at 700: `expected 758 to be less than or equal to 700`.
It also goes green at 760 while the built declaration ends at 763: its reconstructed tag
omits five bytes of Vite whitespace. The replacement tests run the real production and
single-file pipelines in memory, measure the emitted HTML and assert bootstrap ordering
before styles and modules. Both go red at 760 with `expected 763 ... 760`; the actual 1024
limit is restored. No existing honesty assertion is relaxed.

There is no charset-before-bootstrap dependency. I used `head-prepend` as Vite's convenient
injection point. A classic script immediately after charset but before styles and the
application module satisfies the intended ordering. That is the fix I would make if the
budget binds; “that order is what before stylesheets costs” was wrong. Current output is
conformant, so this rebuttal changes the comment and guard, not the injection mechanism.
The test deliberately pins output constraints rather than requiring head-prepend forever.

**Team identities — accept the bug, raise to medium, contest deferral; fixed here.** The
explicit example in `docs/v0.3.0-ideas.md` row 8 was event identity. That explains the audit's
focus, but the resulting fixtures-plus-standings boundary and my broader identity-validation
claim also cover a join used to derive form and next opponents. This was my miss. A JSON
array `["1068"]` becomes `"1068"` under `String`, and the real `tableFor` joined it to a
validated table row in a synthetic payload. “Can only miss” is therefore false: it can
invent an association, with a confident next opponent or form result. A plain object
usually misses; ordinary safe integer IDs normalize legitimately. No occurrence in the
live feed is claimed.

Both ESPN home and away IDs now pass `providerIdentity` before coercion or deduplication.
Missing or invalid IDs reject the event; the provider collects the role, raw ID, event and
competition in its failure diagnostics and the existing boundary aborts the snapshot. I
choose rejection over optional omission because neither a malformed nor an absent ESPN
join key establishes the completeness of that team's derived form/next data. The persisted
schema stays compatible with older snapshots. This increases the set of failures that can
delay publication, making the failure-reader gate more important. New tests went red on
the reviewed mapper and now cover both roles, malformed/absent IDs, valid numeric zero,
