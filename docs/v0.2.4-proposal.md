## Decisions — the brief's five, with reasons

**1. The Node floor: jsdom 30, an `engines` field, and the floor written down.** jsdom 30.0.1
(current) declares `engines.node: ^22.22.2 || ^24.15.0 || >=26.0.0`. CI's `node-version: 24`
resolves to the newest 24.x and clears it; this Mac's 24.15.0 sits exactly on it; the PM VM's
22.23.2 clears it too. jsdom 27 (`^20.19 || ^22.12 || >=24`) would have widened the range at the
cost of two majors, for no machine in the loop. So: `jsdom@^30.0.1`, and `package.json` gains
`"engines": { "node": "^22.22.2 || ^24.15.0 || >=26.0.0" }` mirroring it. **What `engines`
means:** npm prints an `EBADENGINE` *warning* on an older Node and installs anyway (there is no
`engine-strict` here) — it is a signpost, not a gate, and the gate is the moment jsdom fails to
load. Written into `CONTRIBUTING.md`'s run instructions, `CLAUDE.md`'s test paragraph and the
CHANGELOG, as the brief asked. The proof that the floor is real is CI on Node 24 going green on
the PR.

**2. Where the DOM tests live: `tests/dom/*.test.tsx`, with `rig.ts` and `setup.ts` beside
them.** Considered `tests/*.test.tsx` flat (works — `*.test.ts` never matches `.tsx` — but the
exclusion in `tsconfig.node.json` would have to be a glob, and the two support files would have
no home) and `src/**/__tests__/` (puts Testing Library's types and test code into
`tsconfig.app.json`, the build's program). A directory reads clearest: `tsconfig.node.json`
excludes it by name, `tsconfig.test-dom.json` includes it plus `src/vite-env.d.ts` (for
`__APP_VERSION__`), and `tsconfig.json` references all three so `tsc -b --noEmit` checks the
lot. The DOM tsconfig copies `tsconfig.app.json`'s options (DOM lib, `jsx: react-jsx`, the same
strictness) rather than extending it, matching how the other two are written.

**3. The vitest config stays in `vite.config.ts`.** `test.projects` with two inline entries,
each `extends: true` so `define` (`__APP_VERSION__`, which App renders) and the React plugin
reach the DOM project; a `/// <reference types="vitest/config" />` at the top makes the `test`
augmentation explicit instead of riding on the fact that test files import `vitest` into the
same program. It typechecked cleanly, so the `vitest.config.ts` fallback was not needed — one
config file, one `define`, is the reason to prefer it.

**4. One release, not two.** The rig, the affordances and the regressions are one verification
loop: the affordance tests *are* the regressions' fixtures (`primeClock` drives the rollover,
`popTo` drives the `?date=` case), and the deliberate red is meaningless without both. The
review-skill work is a different subject but the same class (tooling), touches nothing the rig
touches, and is two small commits in a PR whose diff is already mostly docs. Splitting would
have made a numbering fork for no independent verifiability. No question went to Beni.

**5. The report: does v0.2.5 split? Yes, cleanly, along the sync/app seam.** The sync half
(row 8: `normalizeEvent` in `scripts/providers/espn.ts`, `sourceId` and the standings doctrine
in `scripts/sync.ts` / `scripts/validate.ts`; row 13d: `inWindow` in `scripts/sync.ts`) and the
app half (rows 6, 7, 12, 13a–c, 11's qualifier: `src/App.tsx`, `src/lib/useUrlState.ts`,
`src/lib/theme.ts`, `src/main.tsx`, `index.html`, three components) share **no file**, and
their proofs are already different loops — a `dry_run` dispatch against the sync half, the full
browser matrix against the app half. v0.2.5 = sync half, v0.2.6 = app half is a cut with
nothing straddling it. Which of them is the first Opus run is Beni's; the fact he asked for is
that the cut exists.

**Also decided here: the gate amendments ship in this PR, not as a micro-patch.** They touch
the file the rename touches, they are the same class, and a micro-patch after v0.2.5 would
leave v0.2.5's own review running with a gate that announces itself last — the exact failure

## The rig — `tests/dom/rig.ts`, and how it reaches the app's own objects

- **`primeClock(at)`** — `vi.useFakeTimers` over `Date`, `setTimeout` and `clearTimeout` only
  (React's scheduler keeps its own primitives), then *holds one subscription* on the app's clock
  store for the test's life. Why: the store resyncs its snapshot when its first subscriber
  arrives, so without a primer App's first render would see the instant the module loaded and
  correct itself a render later — true in production too, harmless there, confusing in a test.
  Vitest's jsdom environment aliases `window` to the global, which is why fake timers reach
  `clock.ts`'s `browser.window.setTimeout` at all. `subscriberCount()` reads one higher than the
  mounted tree while the primer is held; the tests compare counts, never assume zero.
- **`tick(ms)`** — `vi.advanceTimersByTime` inside `act`; the armed timer fires 50 ms past the
  minute. **`wake(at)`** — `vi.setSystemTime` plus a dispatched `focus`, the catch-up path a
  sleeping tab takes. A 24-hour `tick` would fire 1,440 timers and re-render the tree each time;
  `wake` is the honest way to jump a day, and it is also the production path.
- **`popTo(url)`** — `history.replaceState` + a synthetic `PopStateEvent`, verbatim from
  `browser-matrix.md`.
- **`installMatchMedia({ dark, reducedMotion })`** — jsdom has none; the stub answers the two
  queries the app asks and carries inert listener methods so a future `change` listener (row 12)
  installs without a crash. `setup.ts` installs the default (nothing matches) before every file
  and re-installs it after every test.
- **`throwingStorage()`** — replaces the global `localStorage` with one that throws
  `SecurityError` on access; returns the restore. `setup.ts` clears storage after every test
  without a guard, so a leaked hostile storage fails the run loudly — a leaked stub is a
  test-ordering bug and should look like one.
- **`setup.ts`** also wires Testing Library's `cleanup` by hand: RTL's automatic unmount only
  fires when `afterEach` is a global, and this suite imports vitest explicitly. A leaked tree
  would keep the clock subscribed across tests and make every subscriber assertion a lie.

## What the rig found, and did not fix

Nothing new. Three observations, all already on the list or by design, recorded so the next
session does not rediscover them:

- App's first render reads the clock snapshot taken when `clock.ts` loaded; the store resyncs
  when its first subscriber arrives and React re-renders in the same commit. By design
  (`clock.ts`, "A subscriber can arrive after real time has moved on"), invisible in production,
  and the reason `primeClock` exists. A DOM test that forgets to prime sees a one-render-stale
  `today`.
- `?date=2026-13-45` renders today's week and stays in the address bar unnormalised —
  `docs/v0.3.0-ideas.md` row 7's `canonicalSearch()`, v0.2.5.
- `useUrlState`'s popstate effect has no dependency array and re-subscribes every render; the
  `set` identity churns with the inline codecs. Row 7, v0.2.5 — the test "a decoder that throws
  on popstate lands on the initial" is the one that will guard the `useEffectEvent` rewrite.
