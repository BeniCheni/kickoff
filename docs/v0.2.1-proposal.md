**Row 1 (diff-engine blind spots) — true, and wider than written.** `diffFixtures` compares
kickoff (as Brooklyn date, then instant), status, venue, time confidence, and roles only as an
exact pair swap. It never reads `result`, never reads `home.name`/`away.name` outside the swap,
and never reads either team's `sourceId` — so a one-sided rename, a both-sides rename, *and* a
team substitution under the same event id are all silent; the row's "when the sourceId is
unchanged" understates it. A score correction that also moves a league table still opens a PR
(the standings row changed) with no fixture line explaining why; one in a cup, or one that
leaves the table alone, is fully silent — no line, no commit. Design constraints a fixer
inherits: `RESULT_CHANGED` must require *both* results present (the provider sets `result`
only on `full_time`, so a naive inequality fires on every scheduled → full_time transition —
about a hundred lines a weekend); the rename check must be short-circuited by `isInversion`
or the pinned swap test breaks; one club rename touches every in-window fixture of that club
(median 21) — dedupe per team or accept the wall; "urgent for a result inside the horizon" is
vacuous on the schedule path (full time plus one 12 h slot puts a correction about 14 h after
kickoff, outside the −6 h tail; a dispatched or local run is unbounded either way) so urgency needs an explicit override like `STATUS_CHANGED`'s; the report line's
regex is whole-line anchored in `sync.yml` and pinned verbatim in a test, so new kinds fold
into `changes=`/`urgent=` and must not append fields. Cross-track, agreed: this is a
betting-data honesty gap, not a missing report line — a settled score changing silently changes
the basis of a settled bet, and a rename breaks any name-based Step 0 match.

**Row 2 (auto-merge an empty report) — stale on the mechanism, and four design questions.**
There is no dispatched `verify` any more; the check is the PR's own `pull_request` run,
approved by the workflow. The `changed=false` branch has **never executed** in ten real runs
(every run reported `changed=true`, including both dry runs), so it is unproven YAML. Questions
the v0.3.0 proposal must answer: (1) gate on `changed=false` *and* `standings=unchanged` —
`standings=failed` is legal with `changed=false` and would assert a freshness the Table never
had; (2) branch collision — while a change-bearing `sync/scheduled` PR is open, every run
re-detects its changes, and if auto-merge were armed on that PR a later force-push could merge
a human-review-required change; use a separate branch (`sync/quiet`) or `--disable-auto` on the
change-bearing path; (3) the repo has `allow_auto_merge: false`, so `gh pr merge --auto` needs
Beni to flip a setting, or the workflow waits for the approved run and merges plainly; (4) the
squash message — under current settings an empty auto-merge would be indistinguishable in
`git log` from a human-reviewed data change; name it (`sync: nothing moved — <stamp>`). Two
facts for the banner: it reads `meta.json`'s `lastSyncAt`, the Table's freshness line reads
`standings.json`'s `fetchedAt` (a different field), and the app bundles both at import — the
banner goes quiet only after the local checkout pulls `main`, because Step 0 reads
`localhost:5173`. Staging only `meta.json` + `standings.json` on an empty run would keep
twice-daily history to ~2 lines instead of ~2,000 (per-row `fetchedAt` is rendered nowhere).

**Row 7 (`useUrlState` hygiene) — true, with two things the row gets wrong.** Six call sites,
five mounted on the fixtures tab. Only the anchor instance's codecs legitimately change (they
close over `today`); the lens instance's are already module-level, so `setLens` is stable. The
`#hash` is dropped on *every* `set()`, not only when the query empties. The popstate effect's
missing dependency array is currently what keeps the anchor instance's `today`-bound
`initial`/`decode` fresh — a fix that adds `[key]` freezes them and breaks "Back after a
rollover lands on the new today"; React 19.2.8 exports `useEffectEvent`, which is the clean fix — it returns a new wrapper every
render, so capture it inside the `[key]`-keyed effect and never list it in deps.
Normalize-on-load changes only the address bar — with one behavioural consequence to decide:
`?date=<today>` would be normalized away and therefore *un-pinned* across midnight, which is what
"Jump to today" already does. Unknown params survive if the fix edits only its own keys;
`URLSearchParams.toString()` re-encodes a typed `only=pl,laliga` as `pl%2Claliga` on arrival
(it already does on any chip click). No `React.memo` consumer exists, so do not sell the fix on
render performance. No test imports the hook; the pure part (a `canonicalSearch()` in `lib/`)
is node-testable today, the hook itself needs row 5. **Patch, decided:** the hygiene half drives
it, and normalization is a fix to an existing promise ("junk never crashes" already; "junk never
lies" completes the contract) — no new capability.

**Row 8 (warn-and-continue) — true, and there is a worse path beside it.** Two live `console.warn`s
in `scripts/`, not one: `espn.ts:217` (the row's) and `espn-standings.ts:69` (caught two lines
later by the fixed-league-size guard in every practical case). The genuinely silent case is an
un-normalizable event *new to the window*: no `DISAPPEARED` line, and if nothing else changed
the run ends at "Nothing changed" with the warn only in the Actions log. Worse: two id-less events
in one competition both map to `<comp>:undefined` and the chunk-boundary `seen` dedupe drops the
second with no warning at all; the first becomes a persistent phantom row that later syncs
report `DATE_MOVED`/`HOME_AWAY_INVERTED` on. The schema accepts `sourceId: "undefined"`
(`z.string()`, no `.min(1)`). Asymmetry: a missing `date` already aborts (RangeError → exit 2), a
missing `id` is silent, a missing name is a warn. On change-bearing runs the warn *is* in front of
the reviewer — the PR body embeds the whole log — but the checklist has no line for it.
**Doctrine, decided:** every surprise is loud — collect and exit 2, like the other guards, and an
id-less event can never be built.

**Row 9 (period-nav history) — true; deferred, with a hazard recorded.** `history` mode is baked
into each hook instance's single setter, so flipping the `date` instance to `push` also makes the
midnight re-anchor effect push a phantom entry (same URL) once per rollover per open tab, and
"Jump to today" on today push a duplicate. A fix needs a per-call override in `useUrlState` plus a
same-URL guard, and it must preserve the popstate handler's fresh `initial` (row 7's hazard) —
which is why it lands after v0.2.3, not inside it. The one `push`
instance today, the tab, already lacks that guard: clicking the *active* tab pushes a duplicate
entry (`TabNav.tsx:38` has no `key === tab` check), so Back needs an extra press per stray tap

**Row 11 (ticker) — one label-truth fix, two design decisions.** NEXT prints a bare Brooklyn time

advance, not hiding the button. Both are design decisions; the qualifier rides in v0.2.3.

**Row 12 (theme flash) — real for dark users; the fix has a duplication trap.** `html { color-scheme:
light }` and `body { background: var(--bg) }` resolve from `:root` before any script runs; the

prefers matrix and compares it to `resolveTheme`. The `prefers-color-scheme` change listener is
independent and must do nothing for a user with a stored choice.

## Decisions

**Sequencing of the train: tooling → rig → resilience → minor.** The PM's hypothesis put the
resilience patch before the rig; amended, because the error boundary, `useUrlState` and the
re-anchor effect are component wiring — the exact class the ideas file says only a browser has
ever caught — and a rig that lands first means those fixes ship with tests instead of
browser-only proof. v0.2.0's rule ("land the asynchronously-verified item first") is honoured
inside v0.2.3: the sync-side half (row 8, row 13d) is verified by a `dry_run` dispatch and lands
before the app-side half, whose proof is the full browser matrix.

**v0.2.3 stays one release, with a sanctioned split.** Beni approved three patches. The two
halves of v0.2.3 have independent verification loops (dispatch vs matrix), which is exactly the
condition `CLAUDE.md` names for a split; the implementing session may ship them as v0.2.3 and
v0.2.4 if the diff argues for it. The minor stays v0.3.0 either way.

**The skill's three open questions, answered.** (1) The sealed appendix is pasted by a human;
the seal is the point, and a skill that generated leads would be the anti-pattern in a new
costume. (2) `/code-review` is an optional first pass, run only if the session wants a second
net; the skill's own classes are the spine, because the built-in review does not know this
repo's honesty religion. (3) The browser matrix lives as **snippets in a supporting file**
(`${CLAUDE_SKILL_DIR}/browser-matrix.md`), not a checked-in `scripts/verify-matrix.mjs`: the
repo drives the browser through the pane's JavaScript tool, not Playwright, and a script would
be a new dependency for a task the snippets already do. If Playwright ever arrives, the snippets
become the script.

**What this release deliberately does not do.** No app behaviour; no ruleset deletion (Beni's
click); no CHANGELOG edit to `[0.2.0]`'s "ci.yml gains workflow_dispatch so the bot's PR receives
its check" sentence — historically true for what 0.2.0 shipped, superseded in `[0.2.1]`, and Keep
a Changelog convention leaves released sections alone; no fix for the incomplete ladder archives
(the v0.0.3 cycle has no proposal, the v0.2.0 cycle no design or implementation prompt) beyond
making the skill tolerate missing rungs.

**Precedence resolutions to note in the PR.** (a) The skill encodes the *v0.2.0* dynamic-pass
widths (360/375/390/~1000), which `CLAUDE.md` still stated as 390/~1000 — `docs/` process notes
outrank `CLAUDE.md` on method, and `CLAUDE.md` is corrected to match. (b) The plan said "confirm
with `ListSkills`"; that tool lists claude.ai skills and returned nothing for project skills in this
harness, so the skill's own test is "invoke it".
