PREP: elenchus prep <PR> <pass> --runtime <vendor> --model <id> --effort <word> --confirmed-by <name> [--root <dir>]. It reads GitHub only through the gh client, and it pushes nothing.
- Order and SHA. It refuses unless every earlier pass has a valid record, naming the first that does not (T1). The expected SHA is the previous recorded pass's output_sha; if the pull request's head is not that SHA, the branch has moved, and it refuses, naming both.
- The route (the Planner's resolution: schema v1.1 has no field for the next pass's route, so the route arrives as flags, and Sprint 3 decides whether records carry it). It refuses unless all four route flags are given, the vendor, model and effort are in the configuration's table, and that vendor may hold that kind of seat. A Cursor route for a read-only pass is refused, naming S7.
- Where (the Planner's resolution). Worktrees live under a root outside every checkout: ~/.elenchus/seats by default, or --root; a root inside a git working tree is refused. There is one clone per repository under the root, and each seat is a git worktree of it on a local branch of its own at the expected SHA, set to push to the pull request's head branch.
- Open seats (the Planner's resolution). A seat worktree under the root for the same pull request whose pass has no valid record yet is open. prep refuses while one exists, naming its path and pass, and says that removing it (git worktree remove) is how the operator re-routes. A worktree whose pass now has a record does not block.
- Install. npm ci in each configured install directory, inside the worktree; never a shared or symlinked install. Afterwards no symlink under any node_modules may resolve outside the worktree; if one does, prep fails.
- Deny profile (A2, S10). From the configuration's list, in each vendor's own form: Claude Code's permissions.deny in .claude/settings.local.json, Cursor's permissions.deny in .cursor/cli.json, and a Codex .rules file of prefix_rule entries. Each is written into the worktree and excluded from Git through the clone's info/exclude, so the seat can neither commit it nor see it in git status. If a profile's path is tracked at the expected SHA, prep refuses rather than overwrite it. prep prints the launch line for the route: Claude Code with --model, --effort, and --permission-mode plan for a read-only seat; Codex by its binary path (S3) with -m, -c model_reasoning_effort and --sandbox read-only or workspace-write; Cursor with --model, the effort in the id.
- The stamp. The pull request, the pass, the expected SHA, the route, confirmed_by and by_hand true go into an excluded file in the worktree, so the seat's record copies its requested values from it.
- The manifest (T11). git diff --name-status --no-renames from the merge base of the base branch's tip and the expected SHA to the expected SHA, deletions included, written as an excluded file in the worktree that names the merge base.
- When prep finishes, git status --porcelain in the worktree prints nothing.

THE COVERAGE RULE in check (T11). For each pass the configuration marks, compare the record's coverage with the manifest at its input_sha, built from the compare API the same way: a rename counts as a deletion and an addition, and a file list GitHub truncates fails closed, as a truncated compare already does. A marked record with no coverage is UNVERIFIED "coverage not reported": the replay's transcribed records carry none and their sources state none, so none is invented. With coverage present: total equals the manifest's size, every skipped path is in the manifest with a non-empty reason, and reviewed plus the number skipped equals total; anything else is FAIL coverage, naming the path or the numbers. In schema v1.1 reviewed is a count, so a path neither skipped nor actually read cannot be caught; list that as a gap for v1.2.

HANDOFF (T8): elenchus handoff <PR> prints one paste-ready block and runs none of it. It refuses unless every pass has a valid record, check has no FAIL, and the head is release-shaped by the configuration (the version file's version at the head differs from the base's, and the changelog has a section for the new version), naming what is missing. The block follows Kickoff's SKILL.md section 7, step 8: the merge command with its squash message, git tag -a with its message written (the subject is the first sentence of the changelog section), git push origin for that tag, git pull, and the green commands.
