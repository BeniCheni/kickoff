# v0.2.0 — the app's relationship to time (proposal)

*Written 1 Sep 2026 from a fresh read of the repo at `67d9d85` and of PR #5's snapshot, in the
session that reviewed and landed PR #5 (squash `4a55145`). Scope was fixed by Beni before the
audit; this document records the audit, the decisions with their reasoning, the verification
matrix, and what stays unverified — for someone reading cold in six months.*

## Scope (locked)

One release, one subject: **the app's relationship to time.** Data that refreshes itself, a
source that refuses to invent fixtures when it breaks, and a UI whose clock actually ticks.

| Roadmap row | Item | Role | Size |
|---|---|---|---|
| 3 | Unmapped ESPN statuses fail loudly | prerequisite for 13 — an unattended job must not invent scheduledness | S |
| 13 | Scheduled `npm run sync` via GitHub Action, opening a PR | the automation; retires the manual sync (PR #5 was the last) | S |
| 1 | A clock that ticks — `useNow()` | the user-visible feature | M |

Added during the audit (Beni may strike it): **3b** — two more silent-failure paths in the
sync that only matter once nobody is watching the console. The 100-event cap warning becomes
a hard failure, and a league that comes back empty or half-empty aborts the run instead of
writing a couple of hundred "disappeared" fixtures.

Named stretch, declined: row 4 (FixtureRow's stale-LIVE pill). It wants a *designed* state,
and this release has no design brief; a pill invented in an implementation prompt would sit
at the bottom of the precedence ladder (template > design brief > implementation prompt).
Deferred: row 5 (a jsdom component-test rig) — test infrastructure inside a feature release
makes the diff harder to review adversarially; the consequence is a named verification gap
for row 1, stated at the end. Out: rows 2, 7, 11, 12.

## Audit findings

**Row 1 — eight frozen clocks, not six.** `App.tsx` captures `today` once in a memo;
`WeekView` and `MonthView` capture `new Date()` for the hot rows; `NextUpStrip` recomputes only
when `today` or the filters change; `TickerStrip` captures both `today` and `now` at mount;
`StalenessBanner` reads `hoursSinceSync()` at render with nothing to re-render it; and two
sites the roadmap row did not list — `TablePage`'s "synced Nh ago" line, and `lib/standings.ts`
`tableFor`, which calls `todayIso()` *internally*. That last one falsifies the row's
load-bearing claim that the pure layer already takes `nowUtcIso` everywhere: `lib/fixtures.ts`
and `lib/lensSelectors.ts` do, `tableFor` does not, so it gains a `today` parameter and a
test. The estimate stays M. Entangled but untouched: Poster's `TonightSlate` keeps a
`scheduled` fixture in "N REMAINING" after its exact kickoff has passed (it never sees `now`),
while Ledger's Next-up strip drops it — a pre-existing design inconsistency, flagged for a
future brief.

**Row 3 — the fallback.** `scripts/providers/espn.ts` maps ten ESPN status names onto five
statuses and falls back to `scheduled` for anything else — including a *missing* name. In this
session's payloads (live Ligue 1, the four super cups, the test fixtures) only
`STATUS_SCHEDULED` and `STATUS_FULL_TIME` appeared. The names ESPN can emit beyond the map
(`STATUS_DELAYED`, `STATUS_SUSPENDED`, `STATUS_ABANDONED`, `STATUS_FORFEIT`,
`STATUS_FINAL_PEN`, `STATUS_FINAL_AET`, `STATUS_SHOOTOUT`, …) are an **estimate from general
knowledge, not observation** — which is itself the argument for a guard that does not depend
on knowing the list.

**Row 13 — what unattended actually needs.** One workflow exists (`ci.yml`: typecheck → test →
build on Node 24, on push to `main` and every PR). Verified against the repo's settings on
1 Sep 2026:

- The Actions token **cannot create pull requests** today ("Allow GitHub Actions to create and
  approve pull requests" is off). Flipping it is a one-click prerequisite for the owner. No
  secret is needed and none should be added — the README's "no key, no auth, no secrets" is
  worth keeping literally true.
- A PR created by the Actions token **does not trigger `pull_request` workflows**, so `main`'s
  required `verify` check would never appear on the bot's PR and the CI-gate ruleset would
  show it missing. The fix without a secret: a `workflow_dispatch` trigger on `ci.yml`, invoked
  by the sync workflow against the branch head after it pushes. Dispatch runs are the
  documented exception and attach their checks to that SHA.
- `sync.ts` exits **0** (clean), **1** (something inside 72 h moved — *after* writing) and
  **2** (failure — *before* writing). The workflow must treat 1 as "open the PR with a ⚠ title",
  never as failure.
- "Nothing changed" is never literally true: every run rewrites 959 per-row `fetchedAt` stamps
  and `lastSyncAt`, and standings statistics move after every matchday. The reviewable artifact
  is therefore the diff engine's report (`formatChanges` plus standings rank moves), not the
  JSON diff.
- ESPN down or returning garbage: a non-2xx or unparsable body throws → exit 2 → red run, no
  commit, no PR. A standings failure is non-fatal by design (the previous table is kept) and
  the PR body must say so when it happens.
- Runner egress to `site.api.espn.com` was unverified at audit time; confirmed working by a
  live dispatch run before the PR opened (see the verification matrix below — 959 fixtures
  fetched from a GitHub-hosted runner).
- `schedule` triggers only fire from the default branch, GitHub may delay cron runs, and a
  scheduled workflow is disabled automatically after 60 days without repository activity.

**PR #5 — the last manual sync.** 959 → 959 with a 2,194-line diff: 1,918 lines are per-row
`fetchedAt`; nine fixtures actually changed (one FT result, eleven kickoff instants, eight
`round_placeholder → exact`). The eight promotions were Ligue 1's 18–20 September matchday
receiving its TV slots — each moved off the 18:00Z filler onto a real instant, and ESPN live
showed `timeValid: true` with identical instants for all eight. Its 0.1.2 bump was dropped: a
data refresh is not a release, and row 13 is about to make refreshes scheduled.

## Decisions

**Sequencing: 3 → 3b → 13 → 1**, one branch, one PR. Row 13's verification is asynchronous
(dispatch runs, a runner queue, the owner's settings flip); landing it early lets that loop
run while row 1 is built. Row 1 is the largest diff and reviews best last, with the rest
already green. No dependency runs the other way.

**"Fail loudly" means:** map nothing new. An unmapped *or missing* status aborts the run with
exit 2 before any write, and one message lists every offender (status name, competition,
fixture, date) so a single run reports them all. The app therefore never receives a status it
has no design for; the schema's enum and `FixtureRow`'s labels are unchanged. Extra-time and
penalty finals stay unmapped **on purpose**: ESPN's score after extra time is not the 90-minute
result the books settle on, so mapping them to `full_time` would render a confident wrong
score. That needs its own design the first time a synced competition can go to extra time
(none can inside the current window; the four cups are played). Cost, stated: a delayed or
abandoned match anywhere fails the whole refresh until a human adds a one-line mapping. The app
keeps serving the last good snapshot with the staleness banner escalating — which is the
designed degradation, not a failure of it.

**`useNow()`: a module-level clock store read through `useSyncExternalStore`.** `src/lib/clock.ts`
holds a pure, injectable store (`createClock({ now, setTimeout, clearTimeout, listen })`)
whose snapshot is `{ nowUtcIso, today }` with stable identity between ticks; `src/lib/useNow.ts`
is three lines over it. No prop threading, no Provider. What it gives up: per-subtree
overrides (no fake clock via context — the browser proof uses a `Date` shim instead) and
per-consumer granularity (every subscriber re-renders once a minute, which is trivial at this
size). The tick is a **minute-aligned `setTimeout`** re-armed after each tick — never
`setInterval`, which drifts — plus an immediate tick on `visibilitychange`, `focus` and
`pageshow`. Minute granularity is a stated limit: NEXT can flip up to 59 seconds late.

**Midnight rollover: no separate event.** `today` is derived from each tick's instant through
`todayIso` (Intl, Brooklyn time), so a throttled or suspended tab catches up in one visibility
tick and cannot skip a rollover — there is no counter to fall behind. On rollover the Today
pill, `isToday`, the Next-up labels, Tonight's slate and the month frame all move; the
fixtures view re-anchors to the new day **only when no `?date=` is pinned in the URL**, which
is exactly what a reload would do.

**Auto-merge: no.** Argued as data honesty, not convenience. A job that both writes fixture
data and merges it removes the only step where a moved kickoff is checked against an open
position — and this repo is the betting pipeline's Step 0 source. What the human checks is
the PR body's change report: each DATE_MOVED / TIME_CHANGED / HOME_AWAY_INVERTED /
STATUS_CHANGED / DISAPPEARED line is a Step 0 re-verification trigger for any position on that
fixture; DISAPPEARED lines are expected only for cup fixtures leaving the window; standings
moves should agree with the FT results in the same report. How they know to look: the PR *is*
the notification, and its title carries ⚠ when the sync exited 1. One rolling branch and one
open PR, updated in place on every run, keeps the review burden to a single thread. A seam is
left for later: auto-merging an **empty** report becomes defensible only after the diff engine
also reports result corrections and team-name changes — its two blind spots today. That is a
v0.2.x conversation, not this one.

**Tagging: starts here.** An annotated `v0.2.0` on the squash-merge commit. Once bot syncs land
between releases, "the last commit on main" stops meaning "the release", and a tag is how a
release stays findable.

**Semver: 0.2.0, minor.** New user-visible behavior (a ticking clock) and new capability
(scheduled sync, loud sync failures); the URL contract, the data schema and the design tokens
are unchanged; nothing is removed.

**Precedence resolutions to note in the PR.** (a) Branch commits are authored
`Claude <noreply@anthropic.com>` per `CLAUDE.md`, carrying the harness's `Co-Authored-By`
trailer as the repo's squash commits already do. (b) The roadmap's "pure layer is
parameterized everywhere" versus `lib/standings.ts` — parameterize. (c) "Removes the last
manual step" versus no-auto-merge — the *run* is automated, the *merge* is not.

## Shape of the build

Branch `claude/kickoff-v0.2.0-time` off post-merge `main`; ten commits, each green on
`npm run typecheck` and `npm test`; no new runtime dependencies; no new third-party actions
(`gh` is preinstalled on runners, `actions/checkout` and `actions/setup-node` are already in
use).

0. This proposal.
1. Sync: an ESPN status the mapper doesn't know stops the run instead of becoming scheduled.
2. Sync: a truncated or vanished league aborts the run (3b).
3. CI: `workflow_dispatch`, so a sync branch can ask for its own `verify` check.
4. Sync: the scheduled refresh — `sync.yml` (cron twice a day, midnight and noon ET — see the
   review's cadence resolution below; `workflow_dispatch` with a
   `dry_run` input, one rolling branch, one PR, the report in the body), plus a paragraph each
   in `README.md` and `CLAUDE.md`.
5. Clock: the minute-aligned store in `lib`, tested with fake timers.
6. Clock: `useNow()` over `useSyncExternalStore`; `App`'s `today` ticks; the fixtures view
   re-anchors on rollover when unpinned.
7. Clock: hot rows, Next-up and the ticker take the ticking `now`.
8. Clock: the staleness banner and the Table's freshness line escalate on their own;
   `tableFor` takes `today`.
9. v0.2.0 — version, CHANGELOG, README, roadmap rows 1, 3 and 13 marked done.

Then the PR, the adversarial review pass, the squash-merge, the tag, and the first scheduled
run watched.

## Verification matrix

- **Unit, node, every commit.** The existing 83 tests plus: the clock store (fires at the
  minute boundary rather than 60 s after subscribing; no drift across many ticks; an eight-hour
  suspension followed by a visibility tick lands on tomorrow; the DST fall-back night; refcounted
  start/stop; unsubscribe clears the timer); `tableFor(today)` with synthetic rows and fixtures;
  the unmapped-status guard with synthetic events for every mapped name, several unmapped ones
  and a missing one; the cap and shrink guards. Data-honesty assertions are never weakened —
  the statuses being guarded cannot be exercised by the live snapshot, so synthetic fixtures
  are the only coverage they can get.
- **Row 13 — actually run, not just planned.** The owner enabled the Actions PR-creation
  setting first. Two things had to be discovered and worked around before dispatch testing was
  even possible, both recorded here because they're real GitHub behavior, not this repo's bug:
  - `workflow_dispatch` only targets a workflow **path** that already exists on the default
    branch, even when dispatching against a different ref — a brand-new workflow file (unlike
    `ci.yml`, which already existed and just gained a new trigger) can't be dispatched from
    anywhere until something with that filename lands on `main`. Fixed with an inert,
    `workflow_dispatch`-only placeholder `sync.yml` committed straight to `main` (no `schedule:`,
    so it does nothing on its own) purely to register the path; the v0.2.0 PR replaces its
    content wholesale.
  - Dispatched against the feature branch (checkout is intentionally un-pinned, so it resolves
    the *triggering* ref — correct for production, where that's always `main`), the run: fetched
    live ESPN data (959 fixtures, confirmed against the actual step log); ran with `--check` on
    `dry_run=true` and wrote/verified/committed on `dry_run=false`, exactly switching on that
    input; force-pushed `sync/scheduled` and opened
    [PR #7](https://github.com/BeniCheni/kickoff/pull/7); a second dispatch edited that same PR
    (log: "Updated PR #7") rather than opening a duplicate. The dispatched `ci.yml` run's
    `verify` check-run was confirmed attached to the exact head SHA with `conclusion: success`
    via the raw Checks API (`GET /commits/{sha}/check-runs`) on both the first and the
    re-run's SHA.
  - **Residual uncertainty, stated plainly:** the PR's convenience `statusCheckRollup` (what
    `gh pr checks` and the PR page's summary widget read) had not populated after about a
    minute, even though the underlying check-run — the thing GitHub's ruleset actually
    evaluates — was correctly attached and green. Whether that's pure display lag or something
    that would also affect the ruleset's own merge gate was **not settled**, because the test
    PR was independently unmergeable (`mergeable_state: dirty`) for the expected, unrelated
    reason below, which made it impossible to test an actual merge attempt.
  - PR #7 showed `mergeable_state: dirty`/`CONFLICTING`, not because anything is wrong with the
    workflow, but because this test dispatched against the full feature branch (all of v0.2.0's
    commits), so `sync/scheduled` inherited that entire tree against a `main` that only has the
    placeholder — a real production run, checking out `main`, produces a clean data-only branch
    with nothing to conflict on. Closed without merging (never real content) after recording
    all of the above in the closing comment.
  - **Not yet directly observed:** a real, clean, mergeable dispatch-triggered PR actually being
    merge-*eligible* in the GitHub UI. The first genuine post-merge scheduled run is the first
    chance to confirm the check-run display catches up and the merge button is actually live —
    worth a deliberate look, not just an assumption that "the API says success" is the end of
    the story.
- **Row 1 — actually run, not just planned.** In the in-app browser against the dev server, a
  `Date` shim injected into the page (a subclass carrying an offset, `Date.now` included)
  drove the app's own clock instance — reached by importing the exact module URL Vite served
  it under — with a dispatched `focus` event standing in for the tab coming back into view.
  Results at 390 px: (1) unpinned rollover — Sat 12 → Sun 13 Sep moved the Today pill and
  flipped the Next-up labels TOMORROW → TODAY inside the same week; Sun 13 → Mon 14 advanced
  the week view to 14–20 Sep; (2) NEXT and the Broadcast glow — one minute before Union
  Berlin v Schalke (11 Sep 18:30Z) that row was `data-hot` and the ticker read NEXT for it;
  one minute after, both moved to Rennes v Marseille and the passed fixture left the Ledger
  Next-up strip; (3) the banner — hidden at +23 h, amber "Data may have moved… 1 day ago" at
  +25 h, red "Data is stale… 3 days ago" at +73 h, and the Table's line went "under an hour
  ago" → "2h ago" → "3d ago"; (4) subscriber hygiene — the store's count read 4 on Ledger and
  Broadcast fixtures, 3 on Poster and on the Table, and returned to 4 after ten lens switches
  and two tab flips (StrictMode's double subscribe leaves nothing behind); (5) the layout
  matrix — 3 lenses × 2 themes × 2 tabs at 360, 375, 390 and 1000 px, 48 of 48 with
  `scrollWidth === innerWidth`, six 390 px captures taken for the PR, none committed because
  nothing visual changed.
  - **Found and fixed by this pass:** the pinned case failed. With `?date=2026-09-12` in the
    URL, the 12th → 13th rollover dropped the param, because the effect tested "anchor equals
    the day that just ended" — true of any pin on yesterday — and the next Sunday → Monday
    would then have dragged the reader into a week they never asked for. The effect now tests
    the URL for the pin, as this document said it should; re-verified across both midnights,
    and "Jump to today" correctly un-pins it again.

## What stays unverified

- A real overnight — OS sleep and wake, iOS Safari's background suspension — is only
  simulated by the shim and the dispatched `focus`; the catch-up path is proven, the
  platform's willingness to fire it is assumed.
- The `useSyncExternalStore` glue, the re-anchor effect and StrictMode's double subscription
  have no unit test without row 5. The browser scenarios above are their only coverage — and
  they earned it: the one bug this release's verification found lived exactly there.
- The `schedule:` cron trigger itself is proven only by the first scheduled run after merge —
  dispatch testing proves the job's logic, not the cron entry.
- Whether the dispatch-created `verify` check-run's display lag also delays or blocks the
  ruleset's actual merge gate, as opposed to just the PR page's summary widget — the test
  PR's independent, unrelated merge conflict made this untestable here. Watch the first real
  scheduled PR's merge button, not just its API-reported check state, before trusting it.
- Which unmapped status names ESPN really emits is an estimate; the guard is name-agnostic, so
  a surprise fails loudly rather than silently.
